# APS360 Progress Report Delivery Design

## Objective

Produce a reproducible feasibility checkpoint for the cryptocurrency direction-prediction project. The deliverable will contain genuine results from a complete data-to-evaluation pipeline and will support a progress report of at most three pages in the supplied APS360 LaTeX format.

## Submission Scope

The progress checkpoint will demonstrate only the work required by the rubric:

- collected and cleaned hourly BTC and ETH OHLCV data;
- reproducible technical-indicator features and three-class direction labels;
- chronological train, validation, and test partitions without look-ahead leakage;
- momentum and logistic-regression baselines;
- one compact PyTorch CNN-LSTM training run;
- quantitative results, qualitative example predictions, data statistics, confusion matrices, and learning curves;
- a plan to collect later, never-before-seen Binance data for final evaluation.

Multi-horizon experiments, extensive hyperparameter searches, trading profitability claims, and full regime-shift analysis are deferred to the final project.

## Repository Outputs

The implementation will be organized around a single runnable notebook for easy Google Colab submission, with small supporting modules where they improve clarity:

- `notebooks/progress_report.ipynb`: end-to-end reproducible Colab workflow;
- `src/data.py`: Binance collection, cleaning, indicators, labels, and chronological splits;
- `src/models.py`: the CNN-LSTM definition;
- `src/evaluation.py`: metrics, plots, and representative prediction selection;
- `tests/`: focused tests for indicator causality, label alignment, split ordering, and tensor shapes;
- `artifacts/figures/`: report-ready figures generated by the notebook;
- `artifacts/metrics/`: machine-readable run results and configuration;
- `progress_report.tex`: compact report source using `APS360.sty`;
- `requirements.txt` and an updated `README.md`: reproducibility instructions.

Generated market data and model checkpoints will be excluded from Git when they are unnecessarily large. Small summary artifacts needed to audit the report will be committed.

## Data Design

The collector will request Binance public hourly klines for `BTCUSDT` and `ETHUSDT`, paginate safely, deduplicate timestamps, sort chronologically, and validate missing/invalid values. The initial target range is approximately three years, shortened only if the API or runtime creates a deadline risk.

Features will be computed using present and past observations only. They will include OHLCV-derived returns and ranges, RSI, MACD and signal/histogram terms, Bollinger-band position/width, rolling volatility, and normalized volume. The target at time `t` will be the class of the future close return at a fixed forecast horizon. Thresholds will be selected from training data only and then frozen. Rows made incomplete by rolling calculations or future-label construction will be removed.

Samples will use 96-hour input windows. Splits will be chronological, and feature standardization will be fitted exclusively on the training split. Validation and test windows will not cross backward into a way that leaks future labels.

## Model and Baseline Design

The momentum heuristic will map the latest observed return to up, flat, or down using the same class thresholds. Logistic regression will use the most recent engineered feature vector for each sample and will require minimal tuning.

The primary model will accept tensors shaped `[batch, time, features]`. A temporal 1D convolution block will extract local patterns while retaining sequence order. An LSTM will summarize the enriched sequence, and a small fully connected head will output three logits. Training will use cross-entropy loss, Adam, fixed random seeds, class weighting only if training imbalance is material, validation-based checkpoint selection, and a small epoch cap suitable for the deadline.

## Evaluation and Report Evidence

All models will be evaluated on the same held-out chronological test samples using accuracy, macro-F1, per-class recall, and confusion matrices. The neural model will additionally report train/validation loss and accuracy curves, parameter count, and selected correct/error examples with timestamps, true class, predicted class, and probabilities. No financial-return or profitability conclusion will be made from classification accuracy alone.

The report will prioritize four compact visuals: pipeline/model diagram, data/class statistics, baseline-versus-primary metrics with confusion matrices, and the neural learning curve plus representative predictions. Every reported number will be sourced from saved artifacts produced by the runnable pipeline.

## Reliability and Failure Handling

The data collector will retry transient API failures and preserve an existing local cache. Validation will fail clearly for empty responses, duplicate timestamps, nonfinite features, label misalignment, or nonchronological splits. If local CPU training is too slow, the identical notebook will run on Colab GPU without architectural changes. If the neural model performs poorly, the report will state that result honestly and frame the completed pipeline and observed limitations as feasibility evidence.

## Verification

Before completion:

1. run unit tests;
2. execute the pipeline from a clean environment or notebook restart;
3. confirm saved metrics match all tables and captions;
4. compile the LaTeX report and render it for visual inspection;
5. verify main text is no more than three pages and references begin afterward;
6. confirm the notebook contains no credentials and the repository excludes large generated files.

## Authorship and Academic Integrity

The code, figures, and draft prose are support materials. The student must run or inspect the workflow, understand and verify the results, revise the report into wording they can defend, and comply with the course's rules for acknowledging external or AI assistance. Results will not be fabricated and assistance will not be concealed.
